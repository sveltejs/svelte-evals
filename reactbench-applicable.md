# ReactBench Tests Applicable to Svelte

Reviewed [millionco/reactbench](https://github.com/millionco/reactbench) at commit [`11ff042e60ec83a613053fbd721a54ed4dbfdf6f`](https://github.com/millionco/reactbench/tree/11ff042e60ec83a613053fbd721a54ed4dbfdf6f), on 2026-09-07.

**Result: 38 substantive task candidates, 1 optional smoke test, and 13 React-specific tasks to exclude.** These counts cover all 52 task directories, not individual `it`/`test` assertions. Some candidates require substantial redesign; none of the original React harnesses can simply run against Svelte unchanged.

This is an applicability inventory only. No evals, prompts, fixtures, or implementations were converted, and the upstream benchmark was not executed.

## Selection Criteria

A task is applicable when its observable behavior can remain a useful Svelte 5 evaluation: state ownership, asynchronous races, DOM interactions, accessibility, rendering, or server/client consistency. The proposed adaptation should retain the difficult behavior, not merely recreate a similar-looking UI.

The review considered task instructions, metadata, verifier configuration, published behavioral specs/test patches, and reference artifacts where needed. Links below point to pinned task directories, which contain the prompt and verifier. Verifier paths are relative to that task directory.

- **Behavior port:** The behavioral objective survives; replace React components, test rendering, fixtures, and framework-specific dependencies.
- **API redesign:** Also redefine React-specific public APIs, child inspection, render props, or type assertions in Svelte terms.
- **SSR adaptation:** Add a Svelte server-rendering/hydration harness or SvelteKit server loading.
- **Integration adaptation:** Preserve behavior while replacing substantial application/library infrastructure.

These labels describe the kind of work, not guaranteed effort estimates. A behavior port such as a context menu can still be a large task.

## Grading Caveats

- ReactBench's React Doctor gate does not apply to Svelte. Define separate Svelte compilation/type/accessibility checks; they are not an equivalent replacement for every React Doctor rule.
- A converted benchmark needs Svelte-specific starter code that still exposes the intended challenge. Merely translating a React bug can make it disappear under Svelte's reactivity model, especially render-count, effect-dependency, and prop-synchronization tasks.
- Preserve controlled ownership explicitly: a parent can reject a requested change. Do not accidentally weaken these tests into ordinary two-way-binding examples.
- Replace React Testing Library, `renderHook`, `act`, Strict Mode replay, JSX child inspection, and React package/type checks as appropriate. Reuse behavior and browser assertions, not framework internals.
- Prefer Vitest browser-mode component tests for interactions and Playwright for navigation, focus, geometry, gestures, and hydration. Plain parsing/tree/path algorithms can use unit tests.
- Retain fake clocks, deferred promises, abort signals, and deterministic service fixtures where races are the point of the task. New assertions beyond the published verifier should be identified as additions.
- Validate any eventual conversion with a failing starter and passing reference solution. This inventory is a static assessment, not evidence that a converted harness passes those controls.
- The upstream README explicitly asks that benchmark data not appear in training corpora. Keep evaluation use separate from training-data ingestion.
